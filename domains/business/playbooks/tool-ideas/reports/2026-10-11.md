## 1. Bank-feed transaction matching + auto-posting engine

- **Source:** Okoh ERP (`src/lib/accounting/bank-sync/`)
- **Ownership:** `client-engagement` — built under the Okoh engagement, not owned outright.
  Carried over verbatim from the backlog entry (2026-07-14).
- **What it is:** Plaid-connected bank feed, rule-based transaction matcher, GL posting, and
  an exclude flow — the usual reconciliation loop for a small business that currently does
  this by hand.

**Market read:**

This exact feature set is already standard in every mainstream accounting product. QuickBooks
Online, Xero, Sage, and NetSuite all ship bank feeds with configurable matching rules and
auto-posting to the GL ([TechRepublic's 2026 bank reconciliation software roundup](https://www.techrepublic.com/es/article/best-bank-reconciliation-software/)).
Odoo's OCA `account-reconcile` module is a free, open-source version of the same rule engine
([Odoo Apps listing](https://apps.odoo.com/apps/modules/12.0/account_reconcile_rule)). On the
infrastructure side, Modern Treasury and Rutter already sell bank-feed-and-matching as an
API for anyone who wants to build this into their own product
([Rutter integration guide](https://www.treasuryprime.com/blog/rutter-integration-guide-seamlessly-sync-bank-transactions-with-accounting-platforms),
[Modern Treasury via usagepricing.com](https://usagepricing.com/blueprint/stack/modern-treasury)).
A plain "Plaid + matcher + auto-post" build has no gap left to fill — this ground is
thoroughly covered.

One real gap did turn up: Plaid doesn't cover Nigerian banks. Mono, the closest Nigerian
equivalent, was just acquired by Flutterwave (announced January 2026) and is focused on
lending and payments infrastructure, not SME accounting reconciliation
([TechCrunch, Jan 5 2026](https://techcrunch.com/2026/01/05/flutterwave-buys-nigerias-mono-in-rare-african-fintech-exit)).
I found no current evidence Okra is still active as a comparable product. So a
Nigerian-bank-feed reconciliation engine, specifically, is less crowded than the global
version — but that's a different, narrower build than what's in the Okoh codebase today
(which is wired to Plaid, not Mono/Okra), and I can't verify it as a real paying market from
search alone, just an absence of obvious competitors.

**Recommendation:** Not a build/sell candidate as-is. The Plaid-based version competes
directly with QuickBooks, Xero, Sage, Odoo, and dedicated infra vendors with far more
resources — not worth building standalone. If there's a version worth pursuing, it's a
re-scoped one wired to Mono or a Nigerian bank aggregator instead of Plaid, aimed at
Nigerian SMEs specifically. That would need new work, not extraction of the current code —
and extraction isn't on the table regardless, since this was built under the Okoh
engagement. Any move to build, open-source, or sell any version of this depends first on
Alpha resolving the IP/rights question with Okoh. Nothing here clears that.

## 2. Idempotent GRN-to-GL posting engine

- **Source:** Okoh ERP (`src/lib/accounting/posting-engines.ts`, GRN flow)
- **Ownership:** `client-engagement` — same caveat as above. Carried over verbatim from the
  backlog entry (2026-07-14).
- **What it is:** Goods-receipt-to-ledger posting (Dr Inventory / Cr GRNI) that stays
  idempotent across two creation paths reconciling to one ledger effect.

**Market read:**

This is standard mid-market ERP plumbing, not a standalone product category. SYSPRO, Infor,
and Visma.net all document built-in GRN/goods-receipt-to-GL posting with GR/IR clearing
accounts ([SYSPRO help](https://help.syspro.com/syspro-7-update-1/porpgr.htm),
[Visma.net docs](https://help.visma.net/gb_en/financials/online-help/o2c/in-posting-settings-con.html)).
Odoo-adjacent tooling (Shillinq) documents the same Dr Inventory / Cr GR/IR clearing
mechanic for perpetual inventory ([Shillinq docs](https://shillinq.conduction.nl/docs/user-guide/admin/inventory-cogs-posting/)).
I found no dedicated open-source or commercial product that sells this specific mechanic as
standalone IP — it's always a feature bundled inside a bigger ERP, never a separate thing
someone buys on its own. That absence isn't a market gap; it's a sign this doesn't work as
a standalone product. Idempotent posting (dedupe by natural key / stored idempotency key, a
stage-validate-post pipeline) is a known, generic pattern, not something distinctive to
sell.

**Recommendation:** Skip. This is correct, careful engineering, but it's a feature, not a
product — nobody buys "idempotent GRN posting" by itself, they buy an ERP that happens to
do it right. Worth keeping as an internal reference pattern (how we structure posting
engines) rather than a build/open-source/sell candidate. Same rights caveat as above applies
if this were ever reconsidered: it's `client-engagement`, and nothing here changes that.
