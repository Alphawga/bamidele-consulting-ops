## Skipped: Bank-feed matching + auto-posting engine

- **Source**: Okoh ERP (`src/lib/accounting/bank-sync/`) · `client-engagement`
- **Backlog entry** (verbatim): "Bank-feed transaction matching + auto-posting engine (Plaid
  connect, rule-based matcher, GL posting, exclude flow) — generic enough for any small
  business doing manual bank reconciliation."

**Why skipped**: saturated. Xero and QuickBooks Online both ship rule-based bank-feed
matching natively for SMBs, with learning-from-corrections on top of the rules
([Tesorio, "Best Bank Reconciliation Software in 2026"](https://www.tesorio.com/blog/best-bank-reconciliation-software-in-2026-find-the-right-fit-before-you-buy);
[HighRadius, "10 Best Bank Reconciliation Tools"](https://www.highradius.com/resources/Blog/best-bank-reconciliation-tools/)).
The specific niche this idea would occupy — Plaid feed into a self-hosted ERP, rule-based
journal-entry generation, exclude/review flow — is already a maintained open-source project:
[erpnext-bank-bridge](https://github.com/polehntim-commits/erpnext-bank-bridge) (MIT, ~116
commits, v0.4.16) does Plaid OAuth sync, merchant/description/category rules generating
Journal Entry drafts, intercompany-transfer detection, and statement reconciliation — more
scope than the backlog entry describes. Building or open-sourcing a second version of this
adds no market gap. No action.

## Top pick: Idempotent GRN-to-GL posting engine

- **Source**: Okoh ERP (`src/lib/accounting/posting-engines.ts`, GRN flow) · `client-engagement`
- **Backlog entry** (verbatim): "Idempotent GRN-to-GL posting engine (Dr Inventory / Cr GRNI,
  two creation paths reconciled to one ledger effect) — the receiving-to-ledger gap most
  small-business inventory tools leave manual."

**What it is**: a posting engine that takes a goods-received event — regardless of which
code path created it — and produces exactly one GL effect (debit inventory, credit GRNI/Stock
Received But Not Billed), so a GRN created twice, or created through two different flows,
never double-posts or leaves the GRNI account unreconciled.

**Does this already exist?** The accounting pattern itself (Dr Inventory / Cr GRNI, cleared
on invoice match) is standard and implemented in every real ERP — ERPNext calls the liability
account "Stock Received But Not Billed" and documents the same two-sided entry
([ERPNext docs, Perpetual Inventory](https://docs.erpnext.com/docs/user/manual/en/perpetual-inventory)).
Odoo, Cin7 Core, and NetSuite all have equivalent GRNI/accrual modules. So a generic "GRNI
accounting module" is not a gap — full ERPs already cover it for anyone willing to adopt one.

**Where the gap actually is**: the *idempotency across creation paths* part is not solved,
even by the market leader. A live ERPNext issue from 2026 shows the exact failure mode this
backlog entry describes — creating a Purchase Invoice before the Purchase Receipt forces the
"Stock Received But Not Billed" account into a state that breaks goods-in-transit accounting
([frappe/erpnext#59580](https://github.com/frappe/erpnext/issues/59580)). That's the same
two-paths-one-ledger-effect problem Okoh's engine was built to close. The real buyer isn't
"a small business needing GRNI accounting" — it's a dev team building a lighter custom
inventory/ops tool who don't want to adopt a full ERP just to get this one reconciliation
guarantee right, and who would otherwise ship the same bug ERPNext has open today.

**Recommendation: open-source the pattern, not the code — conditional on clearing rights
with the client first.** This is not a standalone product; nobody pays for "an idempotency
library." It's a narrow, well-documented technical pattern (idempotency key design for
dual-entry accounting postings) that's strong authority content for the business domain's
content pipeline, and a small reusable library is plausible as a side asset. Concretely:
- Don't extract or publish any of Okoh's actual source. The generic double-entry bookkeeping
  pattern (debit inventory / credit GRNI, idempotency keys on posting) is not Okoh-specific
  IP and is safe to write about in the abstract.
- Before building or publishing anything closer to the real implementation — a generalized
  library, a code sample, a detailed case-study post — this stays flagged `client-engagement`
  and Alpha needs to resolve what Okoh's contract allows first. Nothing here is clearance.
